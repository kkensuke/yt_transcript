# Homebrew releases

The Homebrew distribution uses two repositories with separate responsibilities:

- `kkensuke/yttext` owns source code, versions, tags, tests, GitHub Releases, and the release workflow.
- `kkensuke/homebrew-tap` owns the generated Homebrew Formula stored at `Formula/yttext.rb` and consumed by Homebrew.

Users install both the CLI and browser app with one command:

```bash
brew install kkensuke/tap/yttext
```

The installed command is `yttext`; use its `web` subcommand to start the browser app.

## Beginner mental model

A Homebrew release involves several GitHub and Homebrew concepts that are easy to confuse at first:

| Term | Meaning in this project |
|---|---|
| Source repository | `kkensuke/yttext`; where development and releases originate |
| Tap | `kkensuke/homebrew-tap`; a separate Git repository from which Homebrew reads the Formula |
| Formula | `kkensuke/homebrew-tap/Formula/yttext.rb`; the Ruby packaging recipe generated by the release workflow and stored in the Tap repository |
| Version | The package version stored in `pyproject.toml` and `src/yttext/__init__.py` |
| Git tag | A named pointer such as `v0.5.0` that fixes the source commit for a release |
| GitHub Release | A human-facing release page attached to a tag; useful for release history but not the package source used by the Formula |
| Fine-grained PAT | A narrowly scoped credential that lets the workflow push the generated Formula to the separate Tap repository |
| `release` Environment | The GitHub Actions Environment named `release` in `kkensuke/yttext`; the release job selects it with `environment: release` |
| Environment secret | A secret value stored inside an Environment. This project stores the Tap PAT as the `HOMEBREW_TAP_TOKEN` Environment secret inside `release` |
| Environment variable | A non-secret Environment value. The current release workflow does not use an Environment variable for the Tap credential |
| GPG signing key | A local cryptographic key used by the project maintainer to create signed release tags |

The important distinction is between **one-time setup** and **per-release work**:

- One time: create the Tap, create its scoped PAT, save that PAT as the `HOMEBREW_TAP_TOKEN` **Environment secret inside the `release` Environment**, and configure a signing key on the maintainer machine.
- Every release: update the version, merge to `main`, create and push a signed `vMAJOR.MINOR.PATCH` tag, then verify the automated workflow.

## Packaging design

The Formula stored at `kkensuke/homebrew-tap/Formula/yttext.rb` builds the tagged source archive in a private Python virtual environment. Runtime and Web dependencies are selected from `uv.lock`, downloaded as SHA-256-pinned source resources, and installed independently of the PyPI wheel.

The Formula uses Homebrew's `python@3.14` and `pydantic` packages. The latter supplies the compiled `pydantic-core` dependency for supported Homebrew platforms. All remaining runtime resources, including `yt-dlp`, FastAPI, and Uvicorn, are generated by `scripts/render_homebrew_formula.py` from the locked dependency graph. Development-only and Windows-only packages are excluded.

This design provides:

- a stable `vMAJOR.MINOR.PATCH` source URL and checksum;
- explicit, reproducible runtime inputs with every declared resource checksum verified by Homebrew;
- the same `yttext` command on Apple Silicon, Intel macOS, and Linuxbrew;
- a Formula test that checks the version, Web command help, and a live `/healthz` response.

## One-time setup before the first release

The Tap repository and scoped release credential must exist before pushing the first release tag. The following setup is normally performed only once, although credentials and signing keys may later need rotation.

### Prerequisites

On the maintainer Mac, make sure Homebrew, Git, and GitHub CLI are available and that GitHub CLI is authenticated:

```bash
brew --version
git --version
gh --version
gh auth status
```

The commands below assume the authenticated GitHub account can create repositories under `kkensuke` and administer `kkensuke/yttext`.

### 1. Create the Homebrew Tap repository

Homebrew maps the short Tap name `kkensuke/tap` to the GitHub repository `kkensuke/homebrew-tap`. Create a local Tap skeleton and publish it to GitHub:

```bash
brew tap-new kkensuke/homebrew-tap

gh repo create kkensuke/homebrew-tap \
  --public \
  --source "$(brew --repository kkensuke/tap)" \
  --push
```

`brew tap-new` creates the local Tap repository with Homebrew's expected structure. `gh repo create ... --source ... --push` creates the public GitHub repository from that local repository and pushes its initial commit.

Verify both the GitHub repository and the local Tap path:

```bash
gh repo view kkensuke/homebrew-tap
brew --repository kkensuke/tap
```

Keep the default Tap branch named `main`. The release workflow pushes the generated Formula to that branch. After the first successful release, the important generated file is:

```text
kkensuke/homebrew-tap
└── Formula/
    └── yttext.rb
```

The Formula is generated by the release workflow in `yttext`, but its persistent home is the separate `homebrew-tap` repository.

### 2. Create a fine-grained PAT for the Tap

The workflow runs in `kkensuke/yttext`, but it must push to a different repository, `kkensuke/homebrew-tap`. The built-in workflow `GITHUB_TOKEN` is scoped to the workflow repository, so this cross-repository write uses a separate fine-grained personal access token.

In GitHub:

1. Click the profile picture in the upper-right corner and open **Settings**.
2. Open **Developer settings**.
3. Open **Personal access tokens** → **Fine-grained tokens**.
4. Click **Generate new token**.
5. Configure the token approximately as follows:

| Setting | Value |
|---|---|
| Token name | `homebrew-tap-release`, or another descriptive name |
| Expiration | Choose an appropriate lifetime and plan to rotate it before expiry |
| Resource owner | `kkensuke` |
| Repository access | **Only select repositories** |
| Selected repositories | `homebrew-tap` only |
| Repository permissions → Contents | **Read and write** |
| Other write permissions | Leave disabled unless a future workflow change requires them |

The important permission boundary is:

```text
kkensuke/homebrew-tap
  Contents: Read and write

kkensuke/yttext
  No PAT access required

Other repositories
  No PAT access required
```

The workflow only needs the token to check out the Tap and run a normal Git commit and push for `Formula/yttext.rb`. It does not need Issues, Pull requests, Actions, or other repository write permissions.

After clicking **Generate token**, copy the token immediately and treat it like a password. Do not put it in a shell script, source file, issue, screenshot, or commit.

### 3. Store the PAT as an Environment secret inside the `release` Environment

The credential belongs in `kkensuke/yttext`, not in `homebrew-tap`, because the release workflow executes from the source repository.

There are two levels to distinguish:

1. **`release` is the name of a GitHub Actions Environment.**
2. **`HOMEBREW_TAP_TOKEN` is an Environment secret stored inside that Environment.**

Open `kkensuke/yttext` on GitHub and go to:

```text
Settings
  → Environments
  → New environment
  → release
```

Inside the `release` Environment, GitHub shows separate sections for **Environment secrets** and **Environment variables**. Put the PAT under **Environment secrets**, not Environment variables:

```text
kkensuke/yttext
└── Settings
    └── Environments
        └── release                         ← Environment
            ├── Environment secrets
            │   └── HOMEBREW_TAP_TOKEN      ← PAT goes here
            └── Environment variables
                └── not used for this PAT
```

Create the Environment secret with:

```text
Name:   HOMEBREW_TAP_TOKEN
Secret: <the fine-grained PAT created above>
```

This distinction matters because the current workflow reads the credential through the GitHub Actions `secrets` context, not the `vars` context:

```yaml
environment: release

# Later, when checking out the Tap:
token: ${{ secrets.HOMEBREW_TAP_TOKEN }}
```

An **Environment secret** is appropriate for credentials such as PATs because GitHub does not display the stored value after it is saved and exposes it to the job through `secrets.NAME`. **Environment variables** are intended for non-secret configuration and are accessed through `vars.NAME`; they are not the correct place for `HOMEBREW_TAP_TOKEN` in this workflow.

Optional required reviewers on the `release` Environment can be used as a manual release gate. If the token expires or is replaced later, update the same `HOMEBREW_TAP_TOKEN` Environment secret inside `release`.

### 4. Configure GPG tag signing on macOS

This project uses signed stable tags as its release policy. Signing is performed on the maintainer machine before the tag is pushed.

If `gpg` is not installed, install GnuPG and the macOS passphrase prompt helper:

```bash
brew install gnupg pinentry-mac
```

Generate a key if you do not already have a suitable signing key:

```bash
gpg --full-generate-key
```

The exact prompts vary by GnuPG version. Unless you have an organization-specific cryptographic policy, the current defaults are suitable for this use. When prompted for identity information:

- The **name is a display label**, not a legal-name requirement. A GitHub username or other recognizable maintainer name is acceptable.
- The **email is important for GitHub verification**. Use an email address associated with and verified by the GitHub account if you want GitHub to show the signature as Verified. A GitHub-provided `noreply` address associated with the account can also be used if preferred.

Check the Git email currently used by the repository before choosing the GPG identity:

```bash
git config user.email
```

After creating the key, list secret keys in long form:

```bash
gpg --list-secret-keys --keyid-format=long
```

A result contains a line similar to:

```text
sec   ed25519/1234567890ABCDEF ...
```

The value after the slash is the key ID. Configure Git to use it, replacing the example ID with the real one:

```bash
git config --global user.signingkey 1234567890ABCDEF
```

For the standard macOS `zsh` setup, make the terminal available to GPG and configure `pinentry-mac`. Add the `GPG_TTY` line only once if it is not already present:

```bash
echo 'export GPG_TTY=$(tty)' >> ~/.zshrc
source ~/.zshrc

mkdir -p ~/.gnupg
echo "pinentry-program $(which pinentry-mac)" >> ~/.gnupg/gpg-agent.conf
killall gpg-agent 2>/dev/null || true
```

Now export the **public** key:

```bash
gpg --armor --export 1234567890ABCDEF
```

Copy the complete block from `-----BEGIN PGP PUBLIC KEY BLOCK-----` through `-----END PGP PUBLIC KEY BLOCK-----`. On GitHub, open:

```text
Profile picture
  → Settings
  → SSH and GPG keys
  → New GPG key
```

Give the key a descriptive title such as `Git Tag Signing - MacBook` and paste the public key. Never upload or copy the private key into GitHub repository content.

GitHub can then associate signatures made by the corresponding private key with the maintainer account when the signing identity meets GitHub's verification requirements.

> `gh release create --verify-tag` is not GPG signature verification. It only makes the release command fail when the referenced Git tag does not already exist in the remote repository. Signed tags are a project release policy enforced by the maintainer procedure, not by that CLI flag.

## Publishing a release

These steps are repeated for every stable release.

### 1. Update and verify the version

Update the version in both places:

- `pyproject.toml` → `[project].version`
- `src/yttext/__init__.py` → `__version__`

Refresh the lock file and run the same important checks used by CI and the release workflow:

```bash
uv lock
uv sync --locked --all-extras
uv run --frozen --all-extras ruff check .
uv run --frozen --all-extras ruff format --check .
uv run --frozen --all-extras pytest
uv build
```

Commit the release changes normally and merge them to `main` before tagging.

### 2. Tag the merged `main` commit

Update the local `main` branch first and confirm there are no accidental local edits:

```bash
git switch main
git pull --ff-only
git status --short
```

`git status --short` should normally print nothing before creating a release tag.

Set the release version, create the signed tag, and verify the local signature. Replace the example version with the release being published:

```bash
VERSION=0.5.0

git tag -s "v${VERSION}" -m "yttext ${VERSION}"
git tag -v "v${VERSION}"
```

Only after `git tag -v` succeeds, push the tag:

```bash
git push origin "v${VERSION}"
```

If `git tag -s` fails, for example because `gpg` is missing or the signing key cannot be used, **do not continue to the push command**. The tag was not created. A later error such as `src refspec v0.5.0 does not match any` usually means Git was asked to push a local tag that does not exist.

### 3. Understand what the tag push triggers

Changing the version number alone does not create a GitHub Release. The release workflow starts when a matching `vMAJOR.MINOR.PATCH` tag is pushed.

The automated flow is shared with the PyPI release:

```text
push vMAJOR.MINOR.PATCH
        ↓
GitHub Actions: Release
        ↓
verify tagged commit is on main
        ↓
verify tag version == pyproject version == package version
        ↓
run lint, tests, and Python build
        ↓
publish the tested wheel and source distribution to PyPI
        ↓
create GitHub Release with generated release notes
        ↓
download and hash the GitHub tag archive
        ↓
render Formula/yttext.rb from uv.lock
        ↓
commit and push the Formula to kkensuke/homebrew-tap
```

The GitHub Release step uses `--generate-notes`, so the basic release notes are generated automatically from GitHub history. Clear pull-request titles therefore improve the generated release notes. The wheel and source distribution are published to PyPI rather than duplicated as GitHub Release assets. See [PyPI releases](pypi.md) for its one-time Trusted Publisher setup.

GitHub also exposes source-code archives for the tag. The Homebrew Formula uses the tagged source archive URL and its SHA-256 checksum; it does not depend on an uploaded GitHub Release package asset.

### 4. Check the workflow result

Open the source repository on GitHub and check **Actions** → **Release** for the tag run. Do not announce the Homebrew release until the workflow has completed successfully and the Tap contains the new Formula version.

If the workflow fails after the tag is already on GitHub, fix the underlying setup or code issue and use GitHub Actions **Re-run jobs** for the existing tag. Do not move or recreate a published release tag just to retry the workflow.

The workflow is designed to be retry-friendly: if the GitHub Release already exists, it does not create it again, and it only commits the Formula when the generated file differs. If PyPI publishing succeeded before a downstream failure, use **Re-run failed jobs** so the immutable package version is not uploaded again.

## Common first-release failures

### `Repository not found` while checking out `homebrew-tap`

Typical causes are:

- `kkensuke/homebrew-tap` has not been created yet;
- `HOMEBREW_TAP_TOKEN` is missing, expired, or invalid;
- the token does not have access to `homebrew-tap`;
- the token lacks **Contents: Read and write** permission.

Fix the Tap or token configuration, update the `HOMEBREW_TAP_TOKEN` Environment secret inside the `release` Environment if necessary, and rerun the existing release workflow.

### `cannot run gpg: No such file or directory`

Install GnuPG:

```bash
brew install gnupg pinentry-mac
```

Then complete the GPG setup above before retrying `git tag -s`.

### `src refspec vX.Y.Z does not match any`

This usually means the preceding tag-creation command failed and the local tag does not exist. Check:

```bash
git tag --list "vX.Y.Z"
```

Resolve the signing problem, create the tag successfully, verify it, and only then push it.

### Release workflow reports a version mismatch

The tag, `pyproject.toml`, and `src/yttext/__init__.py` must all describe the same version. Correct the version on `main` before creating the release tag.

### PAT expired after releases previously worked

Create or regenerate a suitably scoped fine-grained PAT, then replace the value of the `HOMEBREW_TAP_TOKEN` Environment secret inside the `release` Environment. The token value should never be committed to either repository.

## Verifying the Tap

After the Tap update completes, test a source build before announcing the release:

```bash
brew update
brew install --build-from-source kkensuke/tap/yttext
brew test kkensuke/tap/yttext
brew audit --strict kkensuke/tap/yttext

yttext --version
yttext web
```

The first `yttext` release replaces `Formula/yt-transcript.rb` with `Formula/yttext.rb`. Users of the former Formula should migrate explicitly:

```bash
brew uninstall yt-transcript
brew install kkensuke/tap/yttext
```

The explicit install name can be read as:

```text
kkensuke/tap/yttext
   │      │       └─ Formula name
   │      └───────── Tap short name
   └──────────────── GitHub owner

Tap repository: kkensuke/homebrew-tap
Formula file:   kkensuke/homebrew-tap/Formula/yttext.rb
```

Upgrades then follow the normal Homebrew path:

```bash
brew upgrade yttext
```

## Dependency updates

Run `uv lock --upgrade-package PACKAGE` and release a patch version when a runtime resource changes. This is especially important for `yt-dlp`, because YouTube changes can require rapid upstream updates. The Formula renderer fails rather than emitting an unpinned dependency or a package without a source distribution.

Do not normally edit the generated `Formula/yttext.rb` by hand. Change the project dependencies or `scripts/render_homebrew_formula.py`, test the renderer, and let the release workflow regenerate the Formula in `kkensuke/homebrew-tap`.

Homebrew Core can be considered later, after the project has a track record of stable tagged releases and meets Core's notability and maintenance requirements. Until then, the upstream Tap keeps release timing under project control.
